# Specification 0005 — Assurance, Claims and Evidence

**Status:** Proposed architecture, ready for review. **French:** [0005](0005-assurance-model.fr.md).

## Purpose and vocabulary

Report exactly what is established, by which method, for which subject/state and under which assumptions. Never collapse test execution, model checking, theorem proving, implementation conformance, normative fidelity and acceptance into a generic “verified”.

Each record distinguishes claim (falsifiable scoped proposition), argument, evidence (method/tool result), assumption, context, limitation/defeater and authorized decision. A claim about a model is not a claim about implementation without a separate conformance argument.

## Non-interchangeable method classes

Method classes are the primary axis; the word “levels” is reserved for the empirical sub-scale only (SLSA levels, Common Criteria EAL and DO-178C DAL use “levels” on different axes).

For the detailed reconstruction of these distinctions (self-certification vs verification, testimony vs proof, the three assurance questions, evidence statuses), see architecture record [0010 — Assurance, testimony, proof and conformance](../architecture/0010-assurance-proof-and-conformance.md), which complements this specification without replacing it.

### Class 1 — Empirical execution (sub-levels)

| Sub-level | Examples | Establishes | Does not establish |
|---|---|---|---|
| 1a. Unit tests | assert_eq!, Vitest | Expected behavior on the executed cases | Any generality beyond those cases |
| 1b. Integration tests | several components run together | The tested functional path works | Full system composition |
| 1c. Property tests | generated inputs, invariant checks | Properties hold over an enlarged input set | A proof, even over the generated domain |
| 1d. Static analysis | Clippy, TypeScript strict, linters | Certain error categories detected without execution | Actual runtime behavior |

> A test suite, however complete, is not a formal proof.

### Formal and governance classes

2. **Model checking:** explores a formal model under declared bounds/assumptions (TLA+/TLC, Alloy, Spin, CSP/FDR for concurrent-process models); says nothing automatically about implementation.
3. **Program verification:** establishes properties of the program or its specifications in a precise logical setting (Kani, Verus, Dafny, Lean).
4. **Theorem proving:** checker validates a derivation in a specified logic/kernel (Lean, Coq, Isabelle); record axioms, imports, assumptions and escape hatches.
5. **Implementation conformance:** requires explicit refinement/conformance relation and method between implementation and specification.
6. **Normative fidelity:** establishes traceability from approved normative rules to formal rule IDs and faithful human-readable projections.
7. **Acceptance:** governance decision that required claims/evidence/approvals satisfy the predicate for an exact candidate; not proof that all claims are true.

B and Z are also candidate formal-specification/refinement notations; CSP/FDR is a process-algebra/model-checking family for concurrency. They complement but are not interchangeable with model checking, program verification, theorem proving, implementation conformance, normative fidelity or acceptance. See [R-89](../references.md#r-89), [R-90](../references.md#r-90) and [R-91](../references.md#r-91).

## Provable conformance chain (natural language → formal → implementation)

Conformity to a natural-language text (e.g. AGENTS.md) cannot be automatically derived from a program. It is established through a traced chain:

    normative text → approved interpretation (competent human authority, dated, versioned)
                   → formal specification (formal rule with stable ID)
                   → implementation proven conformant to that specification

- Each link is recorded in an interpretation register (stable rule ID, source text revision and digest, approver, date, referenced formal specification).
- Proving the last link does not prove the earlier ones.
- GovCheck never declares “conformant” a case it has not sufficiently verified (unknown is not pass).
- Human-facing projection is deterministic: generated by script from the formal artifacts (Mermaid diagrams, sequence diagrams from TLC traces), never produced directly by an LLM. Generated HTML documentation served to validators is a versioned artifact with drift checking, like the lifecycle diagram.

## Evidence record

Bind stable evidence/claim IDs; subject kind and native immutable identity; repository and exact base/candidate fingerprints; governance package revision/semantics; specification/model revision; method and scope; tool/version/configuration/invocation; environment, assumptions, bounds and external inputs; raw result or integrity-protected reference; outcome/time/producer/provenance; limitations and invalidation dependencies. A bare exit code proves only the outcome of that invocation.

Claims declare acceptable methods, scope, freshness and corroboration. Evidence can support, refute or leave a claim inconclusive. Contradictory evidence remains visible. Assurance arguments decompose top-level claims into subclaims, assumptions and evidence; circular reasoning must not be presented as proof.

## Formal methods and trusted base

For theorem proving, record logic, kernel/checker version, axioms, imported theorems, admitted obligations, unsafe features, oracles and reproducibility. If Lean is selected, account explicitly for sorry, unreviewed axioms, unsafe, native oracles and dependency trust.

For model checking, record model revision, configuration/constants, reductions, fairness, state/transition counts, bounds and completion status. Bounded/partial exploration is never called exhaustive.

For conformance, record implementation/spec revisions, refinement relation, abstraction boundary and method. For normative fidelity, record approvers and source-to-rule-to-projection traceability.

## Provenance, trust and freshness

Hashes/signatures may establish integrity/origin under key assumptions, not semantic correctness, authorization or truth of external data. External facts need source, retrieval time, validity and trust classification. Disclose the trusted computing base: evaluator, parser/canonicalizer, VCS adapters, evidence verifiers, crypto libraries, runtime and remote authorities.

Evidence declares dependencies. Changes, tool/key compromise, source correction or discovered defects may invalidate it. Preserve historical records; exclude invalid evidence from current decisions unless revalidated.

## Reporting and conformance targets

Report claims, status, evidence, assumptions, limitations, state binding, provenance, unresolved defeaters and exact acceptance decision. Distinguish not-run, not-applicable, unsupported, incomplete, failed and passed; avoid unexplained aggregate scores.

A conforming implementation binds evidence to exact states/governance revisions, exposes assumptions/TCB, preserves contradictions and invalidations, distinguishes bounded from exhaustive exploration, accounts for proof axioms/kernel, and requires conformance evidence before implementation-level claims. No engine or proof infrastructure exists yet.
